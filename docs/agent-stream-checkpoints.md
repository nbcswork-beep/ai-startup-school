# Project generation across function limits

The agent's existing 250-second run budget stays inside the 300-second function limit. A large site can span the initial run and up to three automatic continuations, using the existing persisted job and browser continuation flow. No paid hosting feature or additional service is required.

Previously, adapters assembled all tool arguments in memory and emitted a tool call only when the entire provider response ended. A deadline inside `create_project` discarded even code that had already arrived. Instructions to write smaller files alone did not fix that case.

OpenAI-compatible and Anthropic adapters now expose argument snapshots while receiving them. Only offered built-in project tools with `files:write` may checkpoint. The agent saves valid file paths and the text received so far, at most once every 750 ms, with a final flush on interruption. A piece that arrives inside the 750 ms window is saved when the window ends, even if the model then pauses, so a crash during the pause keeps it. A draft write that fails (a storage hiccup) does not end the run: the next piece saves it, and the final flush is retried twice. The partial JSON reader does not evaluate code or invent missing characters. Existing ownership, path, project size and file count restrictions apply.

Checkpoints are private drafts with `incompleteFiles`. Their preview says the code is being written, and publication is refused. An existing published snapshot keeps serving unchanged. A complete successful tool call validates and finalizes the same project ID.

Checkpoint saving no longer depends on `kind` appearing before `files` or `index.html` being the first file. Received CSS/JS/text is saved immediately once its safe path is available. When the type has not arrived yet, the private ZIP uses a provisional code container with `projectKindPending`; `read_project` exposes `kind: null` and asks the model to resolve it through `write_project_files(kind=...)`. Website drafts may lack their entry page; that missing page is tracked as incomplete, and publication still requires it. File paths, size limits, ownership, and validation of completed code remain enforced. The project tool description and agent rules consistently request small writes, including when a stored skill asks for complete files.

Continuation reads `read_project` for each file's `chars` and `incomplete`, reads the file tail, then uses `append_project_file` with the exact saved character offset and only new text. An incorrect offset is rejected. Streamed append finalization uses the original baseline so the checkpointed tail is not appended twice. `complete=true` validates the file and clears its unfinished flag. Replacing a complete file through `write_project_files` also clears that flag.

The existing browser automatically submits eligible continuations, including after returning to a chat. Stop and the three-continuation cap still apply. Work is not guaranteed to continue while the browser is closed.

A deadline before the first file now also permits a continuation. Finalization persists the original request, attachments, selected skill and an honest interruption message, so the next run has the original context. The server uses a separate retry prompt when the last run saved no files: inspect an existing project if available, otherwise save a small first file and build the full requested result in parts. The retry does not claim that code was saved, and the UI does not label an empty run as a completed part. Repeated triggers still join one job, and three unsuccessful continuations end with an explicit message instead of an endless loop. A provider that sends no code still cannot be checkpointed; retries improve recovery but cannot guarantee that provider will respond. Each attempt uses the existing token reservation and settlement rules.

Regression coverage: interrupted HTTP streams for both protocols; partial escaping and Unicode; API generation, persistence, continuation, and published asset delivery; output-token truncation; exact offsets; one stable project; publication protection; ownership and unsafe paths; stale checkpoint protection. Tests use a local scripted provider, not the live paid provider.
